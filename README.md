## 2. 結論：見習い料理人の作法は、もうシェフには要らない

たとえるなら、**見習い料理人が、やがて自分の店を持つシェフになる物語**。見習い時代は「分量を1gも間違えない」「手本の写真通りに盛り付ける」ことが正義だった。だが経験を積んだシェフに同じ作法を強いると、逆に動きが鈍くなる——今回の発表はこれと同じ構造だ。✅

- **POINT 1**: Claude 5世代のモデルは、細かいルールより「良い道具（インターフェース）」と「裁量」を与えたほうが性能が上がる
- **POINT 2**: この転換は6つの「Then→Now」に整理できる（4章で詳説）
- **POINT 3**: Anthropicはこの知見を`/doctor`コマンドに実装済み。自分の環境でも今すぐ確認できる

## 3. 核心：システムプロンプト80%削除の中身

Claude Codeのシステムプロンプトには、かつて「コードではデフォルトでコメントを書かない」「複数段落のドキュメント文字列は書かない」といった、かなり強いガードレールが並んでいた。✅ 理由は、古いモデルにはこうした縛りが無いとコメントの書きすぎ・大仰なドキュメント作成などの"やらかし"が多かったから。✅

新しいシステムプロンプトでは、これが「周囲のコードのように読めるコードを書く：コメントの密度・命名・イディオムを合わせる」という一文に置き換わった。✅ 具体的にどうすべきかを列挙する代わりに、Claude自身の判断に委ねる書き方に変わったということだ。✅

## 4. Then→Now：6つのルール転換を1つずつ

見習い料理人とシェフの比較で見ると分かりやすい。

| Then（見習い時代） | Now（シェフになった今） | たとえるなら |
|---|---|---|
| ルールを一つずつ与える | 判断そのものを委ねる | 分量を寸分違わず測る見習い → 味見で仕上げるシェフ |
| 手本の見本写真を見せる | 良い道具・材料（インターフェース）を渡す | 見本皿の写真を模写する見習い → 良い鍋と食材で工夫するシェフ |
| 必要な情報を全部前出しする | 必要な時に必要な分だけ開示する（段階的開示） | 分厚いレシピ本を最初から全部読む見習い → 必要なページだけ引き出すシェフ |
| 同じ指示を繰り返し伝える | 道具そのものにシンプルな説明を持たせる | 何度も口頭で確認する見習い → 一言のラベルで伝わるシェフ |
| メモを手作業で記録させる（CLAUDE.md手動追記） | 関連する学びを自動で記憶する（自動メモリ） | ノートに手書きするだけの見習い → 体が覚えているシェフ |
| 一言だけの簡易な仕様書 | 詳細な参照資料（HTML・テストコード等）を渡す | 一言メモだけの見習い → 仕込み表・写真つき資料を使うシェフ |

✅（6項目とも公式ブログ本文で直接確認）／たとえ話は本資料側の解釈

## 7. 反論の先回り・注意点

**「これはOpusやFableだけの高级モデル限定の話では？」**——公式記事はOpus 5・Fable 5を主な例として挙げているが✅、書かれている6つの原則（判断を委ねる・インターフェース設計・段階的開示等）自体はモデル非依存の考え方であり、Sonnet 5やHaiku 4.5を使う場合でも設計方針として参考にできる。⚠️（この一般化は記事本体の主張ではなく、本資料側の解釈）

**「制約を全部やめていいということ？」**——そうではない。記事は「最悪のシナリオを避けるための制約」自体を否定していない。✅ あくまで「モデルの判断力が上がった分、過剰だった制約を見直せる」という話であり、境界設定（何をしてはいけないか）自体は今も必要と読める。⚠️

**「今すぐ全部書き換えるべき？」**——公式記事も「`claude doctor`で棚卸ししてから」という手順を推奨しており✅、いきなり全部を消すのではなく、まず現状を診断してから判断するのが安全。
